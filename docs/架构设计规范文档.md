## 1. 选题确定与环境适配结论

### 1.1 选题确定

在上一轮备选题目中，结合**本机实际环境**与**四项硬性要求**，确定选题为：

> **基于 Spring Boot + uni-app 的校园场馆预约与拼场组队系统的设计与实现**

**选题理由（环境适配）**

| 环境事实 | 探测结果 | 结论 |
|---|---|---|
| JDK | Eclipse Temurin **17.0.20** | 支持 Spring Boot 3.x，选型锁定 Spring Boot 3.2.x |
| 构建工具 | Maven **3.9.12**，**无 Gradle** | 全项目统一 Maven，不引入 Gradle 多构建体系 |
| 数据库 | 本机 **MySQL 8.0** 已安装 | 本地开发直接用原生 MySQL，不依赖容器 |
| 容器 | **无 Docker** | 本地开发走 `mvn spring-boot:run` / `java -jar` + 原生 MySQL；Docker 仅作为服务器端可选部署方案 |
| Node.js | 已安装（含 npm） | uni-app（Vue3+Vite）与管理端（Vue3+Element Plus）可直接构建 |
| GPU / AI 框架 | 无 | **放弃 YOLO、ModelArts 类选题**（训练与推理环境不具备） |
| 地图 / 支付 / 短信资质 | 无企业主体 | **放弃强依赖地图 Key、微信支付、短信验证码的选题**，全部改为自研或模拟实现 |

**为什么从三个详案中选它**：① 与已列出的 16 个题目无重复；② **零外部资质依赖**（不需要地图 Key、支付商户号、短信签名、GPU），在现有环境下 100% 可落地；③ 自带算法型难点（时段冲突检测、候补递补、动态签到码、信用分），论文与答辩有内容可写；④ 天然满足"多端互动"验收点（学生预约/拼场 → 队友与管理员端收到实时消息）。

### 1.2 建设目标

1. 一套后端 + 三个端：**学生端（小程序/H5/APK 三合一）**、**管理端（Web）**、**签到终端（复用小程序扫码）**。
2. 前端任何增删改（预约、取消、拼场、场馆配置）都经后端业务处理并落库，可当场用 SQL 验证。
3. 多端实时互动：预约成功、拼场邀请、满员成团、候补递补、违约扣分、管理端封禁时段，均在秒级推送到相关端。
4. 部署到公网服务器，通过 **HTTPS 域名**从校园网、4G/5G、家庭宽带均可访问。
5. 每位成员在 GitHub 远程仓库留下**可追溯的独立提交记录**。

### 1.3 四项硬性要求 → 架构落点

| 项目要求 | 文档中的落点 |
|---|---|
| （1）前后端 + 数据库 | 第 4 章总体架构、第 5 章技术选型、第 8 章数据库规范 |
| （2）多端系统 | 第 4.2 节多端形态、第 10 章多端互动与消息规范 |
| （3）每人有 GitHub 提交记录 | 第 12 章编码与 Git 规范（分支模型 + 提交规范 + 留痕校验） |
| （4）部署到服务器 | 第 13 章部署架构与规范 |

## 2. 需求概述

### 2.1 角色与权限

| 角色 | 端 | 核心权限 |
|---|---|---|
| 学生（USER） | 小程序 / H5 / APK | 浏览场馆、预约、取消、发起拼场、加入拼场、扫码签到、查看信用分与消息 |
| 场馆管理员（VENUE_ADMIN） | Web 管理端 | 维护场馆/场地/开放规则/价格、审核与强制释放预约、查看使用率热力图、黑名单管理 |
| 系统管理员（SYS_ADMIN） | Web 管理端 | 用户与角色管理、信用分规则配置、操作日志、数据统计与导出 |
| 签到终端 | 小程序扫码页 / 管理端扫码页 | 校验动态签到码、写入签到记录（无独立账号，由前两类角色承载） |

### 2.2 核心用例

1. **预约**：选择场馆 → 选择场地 → 选择日期与连续时段 → 提交 → 冲突检测 → 生成预约单（支付为模拟）→ 推送确认消息。
2. **取消**：预约开始前 2 小时可免费取消；逾期取消计违约。
3. **拼场组队**：发起人设定场地、时段、人数上限（如 4 人）、AA 费用 → 生成邀请 → 队友接受/拒绝 → 满员成团 → 生成正式预约单。
4. **候补排队**：时段已满时可加入候补队列 → 他人取消触发自动递补 → 推送递补消息（10 分钟内未确认则顺延下一位）。
5. **签到与违约**：到馆出示动态二维码 → 终端校验 → 签到成功；超时未签到自动置为 `NO_SHOW` 并扣信用分。
6. **信用分与黑名单**：初始 100 分，履约 +1（封顶 100），违约 −5；低于 60 分限制预约，连续 3 次违约进入黑名单 7 天。
7. **统计**：场馆时段使用率热力图、预约量与取消率趋势、活跃用户排行。

### 2.3 关键状态机

**预约单 Reservation.status**

```
CREATED ──支付(模拟)成功──> CONFIRMED ──扫码签到──> SIGNED ──结束──> FINISHED
   │                            │
   │超时未支付                   │开始时间+15min未签到
   ▼                            ▼
EXPIRED                      NO_SHOW ──> (扣信用分)
   ▲
   └── 用户取消(开始前>2h) ── CANCELLED ； 开始前≤2h 取消 ──> CANCELLED_LATE(计违约)
```

**拼场队 Team.status**

```
RECRUITING ──申请/邀请被接受且人数达上限──> FULL ──发起人确认──> CONFIRMED ──> 生成预约单
    │                                          │
    │发起人解散 / 时段开始前未成团                │成员退出(重新回到 RECRUITING)
    ▼                                          ▼
DISSOLVED                                   RECRUITING
```

**候补队列 WaitingQueue.status**：`WAITING → NOTIFIED → CONFIRMED | EXPIRED | CANCELLED`

## 3. 设计原则与约束

1. **不过度设计**：采用「模块化单体（Modular Monolith）」而非微服务。理由：团队 3–4 人、8 周工期、本机无容器编排环境，微服务会显著增加部署与调试成本，而验收不考察服务拆分。
2. **分层清晰**：Controller → Service → Mapper → DB，禁止 Controller 直连 Mapper，禁止在 Controller 写业务判断。
3. **契约先行**：先定接口文档与错误码，再并行开发前端与后端。
4. **数据一致优先**：涉及预约额度的写操作必须走事务 + 数据库唯一约束兜底，不允许仅靠应用层判断。
5. **可演示优先**：每个模块必须能在本地一条命令启动并被验收人员直接操作。
6. **可降级**：Redis、MinIO 等非必需组件缺失时，系统须能降级运行（见 5.3）。

## 4. 总体架构

### 4.1 分层架构

| 层次 | 职责 | 主要组件 |
|---|---|---|
| 客户端层 | 交互与展示 | uni-app（学生端：小程序/H5/APK）、Vue3+Element Plus（管理端）、扫码页 |
| 接入层 | 反向代理、HTTPS、静态资源、跨域 | Nginx（服务器）/ Vite DevServer（本地） |
| 应用层 | 认证鉴权、业务编排、事务、消息推送 | Spring Boot 3.2（Controller / Service / WebSocket / Scheduler） |
| 领域与数据访问层 | 领域对象、状态机、持久化 | 领域 Service、MyBatis-Plus Mapper、Redis 缓存 |
| 数据层 | 结构化数据、缓存、文件 | MySQL 8、Redis 7（可选）、本地磁盘 / MinIO（可选） |
| 支撑层 | 日志、接口文档、监控 | Logback、Knife4j(OpenAPI3)、Actuator |

**依赖规则**：客户端层只依赖接入层暴露的 HTTP/WS 接口；应用层内部只允许上层调用下层；跨模块调用必须通过 Service 接口，不允许跨模块直接改表。

### 4.2 多端形态与实现策略

| 端 | 技术 | 构建产物 | 说明 |
|---|---|---|---|
| 学生端-小程序 | uni-app → `mp-weixin` | 微信开发者工具导入 | 演示主端；因无企业主体，支付走模拟、消息走 WebSocket + 站内消息中心 |
| 学生端-H5 | uni-app → `h5` | 静态站点，Nginx 托管 | 满足"不同网络访问"，无需装微信即可验收 |
| 学生端-APK | uni-app → `app`（HBuilderX 云打包） | Android APK | 体现"多端"，安装后即可跑通主流程 |
| 管理端 | Vue3 + Vite + Element Plus + ECharts | 静态站点 | 场馆配置、审核、统计大屏 |
| 签到终端 | uni-app 扫码页（复用学生端工程） | 同小程序 | 调 `uni.scanCode` 校验动态码 |

> **一套代码多端产出**是本节的核心决策：使用 uni-app 条件编译（`#ifdef MP-WEIXIN / H5 / APP-PLUS`）隔离平台差异，避免维护三套前端。

### 4.3 部署拓扑（逻辑）

```
[学生小程序/APK]  [学生 H5]  [管理员浏览器]  [签到扫码]
        │              │            │              │
        └──────────────┴───── HTTPS(443) ──────────┘
                              │
                         [Nginx]
                    ├── /            → 前端静态资源(dist)
                    ├── /admin       → 管理端静态资源
                    ├── /api/**      → 127.0.0.1:8080 (Spring Boot jar, systemd 守护)
                    └── /ws/**       → WebSocket 升级
                              │
                    [Spring Boot 3.2 单实例]
                       ├── MyBatis-Plus → [MySQL 8] (仅监听 127.0.0.1)
                       ├── Redis 7 (可选，不可用时降级)
                       └── 本地磁盘/MinIO (可选，存头像与工单照片)
```

### 4.4 关键架构决策（ADR 摘要）

| 编号 | 决策 | 备选 | 理由 |
|---|---|---|---|
| ADR-01 | 模块化单体 | 微服务 | 人力与工期不足，部署环境无容器编排 |
| ADR-02 | Spring Boot 3.2 + JDK 17 | Spring Boot 2.7 + JDK 8 | 本机已是 JDK 17，无需降级安装 |
| ADR-03 | 时段按 30 分钟**槽位表**落库 + 唯一索引 | 仅区间重叠 SQL 判断 | 唯一索引在数据库层杜绝并发超卖，见 9.1 |
| ADR-04 | Sa-Token 做认证鉴权 | Spring Security | 上手成本低、与 WebSocket 结合简单，8 周内更稳 |
| ADR-05 | WebSocket(STOMP) 为主，轮询兜底 | 纯轮询 | 满足"秒级多端互动"验收观感，轮询保证弱网可用 |
| ADR-06 | uni-app 一套代码出三端 | 分别开发小程序与 Web | 人力有限，且必须体现"多端" |
| ADR-07 | Redis 设为可选依赖 | 强制依赖 Redis | 本机未确认安装 Redis，需保证零依赖也能跑通（降级方案见 5.3） |

### 5.2 环境约束下的操作规范

1. **统一 JDK 17**：`JAVA_HOME` 指向 Temurin 17；`pom.xml` 中 `maven.compiler.source/target=17`，禁止使用 JDK 21 预览特性（部分成员机器可能未升级）。
2. **统一 Maven**：仓库统一走阿里云镜像（`settings.xml` 提交到仓库 `docs/dev/settings.xml`）；禁止提交 `target/`。
3. **本地启动方式**（无 Docker）：
   - 数据库：本机 MySQL 8 执行 `docs/sql/V1__init.sql` 建库建表；
   - 后端：`mvn spring-boot:run -Dspring-boot.run.profiles=dev`；
   - 前端：`npm i && npm run dev:h5`（学生端）/ `npm run dev`（管理端）。
4. **服务器端**：优先使用 `systemd + jar`（不依赖容器）；若服务器可使用 Docker，则用 `docker-compose.yml`（MySQL + Nginx + App）作为可选方案，两套方案在 `deploy/` 目录并存。
5. **禁止引入 Gradle**：全仓库单一构建体系，降低环境差异。

### 5.3 可选组件的降级方案

| 组件 | 缺失时的影响 | 降级实现 |
|---|---|---|
| Redis | 无法用分布式锁与缓存 | 改用 **Caffeine 本地缓存 + MySQL 唯一索引 + `SELECT ... FOR UPDATE`**；签到 token 落库并设过期时间 |
| MinIO | 无法用对象存储 | 存本地磁盘 `./data/upload`，Nginx 直接托管 `/upload/**` |
| WebSocket 被校园网阻断 | 消息不实时 | 前端自动降级为 5 秒轮询 `/api/v1/notifications/poll` |
| 小程序订阅消息 | 无微信推送 | 只用站内消息中心 + H5 浏览器通知（权限申请可选） |

> 判定标准：**在没有 Redis、没有 MinIO、没有微信推送的环境下，系统仍须完整跑通验收流程。**

## 7. 接口设计规范

### 7.1 通用约定

- 风格：RESTful；基础路径 `/api/v1`；资源用复数名词，动作用子资源或明确动词。
- 方法：`GET` 查询、`POST` 新增、`PUT` 全量更新、`PATCH` 局部更新、`DELETE` 删除。
- 认证：请求头 `Authorization: <token>`（Sa-Token），登录接口除外。
- 分页：请求 `pageNum`（从 1 开始）、`pageSize`（默认 10，上限 100）；响应 `records/total/pageNum/pageSize`。
- 时间：统一 `yyyy-MM-dd HH:mm:ss`，时区 `Asia/Shanghai`，数据库用 `datetime`。
- 幂等：创建预约携带客户端生成的 `requestId`，服务端唯一索引去重。
- 接口文档：Knife4j 自动生成，访问 `/doc.html`，每新增接口必须补注解。

## 8. 数据库设计规范

### 8.1 通用规范

1. 引擎 `InnoDB`，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。
2. 所有表含公共字段：`id BIGINT UNSIGNED AUTO_INCREMENT` 主键、`create_time`、`update_time`、`deleted TINYINT DEFAULT 0`（逻辑删除）。

4. 状态字段用 `TINYINT` 并配 Java 枚举，禁止裸写魔法数字；枚举含义写入注释。
5. 索引规范：外键字段、状态字段、时间范围字段建索引；组合索引遵循最左前缀；联合唯一索引用于业务唯一约束与防超卖。

## 9. 关键业务设计

### 9.1 时段冲突检测与防超卖（核心算法）

**问题**：MySQL 无区间排他约束，仅用 `WHERE start < newEnd AND end > newStart` 判断存在并发漏洞（两个请求同时读到"空闲"）。

**方案（双保险）**

1. **槽位化**：把开放时段按 30 分钟切成槽位，一次预约 = 连续 N 个槽位。
2. **唯一索引兜底**：`uk_court_date_slot (court_id, slot_date, slot_no)` 保证同一场地同一槽位只能被一条记录占用，并发写入时第二条必然抛 `DuplicateKeyException`。
3. **事务内批量插入 + 冲突回滚**：全部槽位插入成功才提交，任一失败整体回滚并返回 `30001 时段已被占用`。
4. **Redis 分布式锁（可选优化）**：`lock:resv:{courtId}:{date}`，减少无效回滚、提升并发体验；Redis 不可用时直接跳过（正确性仍由唯一索引保证）。

```java
@Transactional(rollbackFor = Exception.class)
public ResvVO create(CreateResvDTO dto, Long userId) {
    // 1. 校验：场地存在、日期在开放规则内、信用分≥阈值、时长≤单次上限
    validate(dto, userId);
    // 2. 生成预约单（待支付）
    ReservationDO resv = buildReservation(dto, userId);
    reservationMapper.insert(resv);
    // 3. 循环占用槽位 —— 并发冲突由唯一索引拦截
    for (int slot : expandSlots(dto.getStartTime(), dto.getEndTime())) {
        try {
            slotMapper.insert(new SlotDO(dto.getCourtId(), dto.getResvDate(), slot, resv.getId()));
        } catch (DuplicateKeyException e) {
            throw new BizException(ResultCode.SLOT_OCCUPIED, "该时段已被预约，请选择其他时段");
        }
    }
    // 4. 写消息并推送
    noticeService.push(userId, NoticeType.RESV_CREATED, resv);
    return toVO(resv);
}
```

### 9.2 候补队列与自动递补

- 触发点：预约取消 / 过期 / 未签到释放 → `releaseSlots()` 后调用 `queueService.tryPromote(courtId, date, slotNos)`。
- 递补逻辑：按 `create_time` 升序取队首 → 置 `NOTIFIED` 并设 `expire_time = now + 10min` → 向该用户推送消息 → 用户确认则生成预约单，超时未确认由定时任务置 `EXPIRED` 并顺延下一位。
- 定时任务：`@Scheduled(fixedDelay = 60000)` 扫描 `status=NOTIFIED AND expire_time < now`；单实例部署，无需分布式调度。

### 9.3 动态签到码

1. 学生在预约开始前 15 分钟至开始后 15 分钟内，请求 `/checkin/code`。
2. 服务端生成一次性 token：`token = Base64(resvId + expireAt + HMAC_SHA256(resvId|expireAt, serverSecret))`，写入 DB/缓存并设 60 秒 TTL。
3. 终端扫码后 `POST /checkin/scan` 校验签名、有效期、未使用；成功后置预约 `SIGNED` 并写 `checkin_record`；token 立即失效，防截图复用。
4. 超时未签到：定时任务将 `CONFIRMED` 且 `start_time + 15min < now` 的预约置 `NO_SHOW`，释放槽位，扣信用分并推送。

### 9.4 信用分规则

| 事件 | 分值 | 说明 |
|---|---|---|
| 正常签到并完成 | +1（上限 100） | 每日最多 +2 |
| 超时未签到 | −5 | 同时释放槽位、记违约次数 |
| 开始前 2 小时内取消 | −3 | 2 小时外取消不扣分 |
| 拼场成团后临时退出 | −3 | 影响其他成员 |
| 连续 3 次违约 | 进黑名单 7 天 | 阈值与时长由 `sys_config` 配置 |

信用分变动必须写 `credit_log`，禁止直接 UPDATE 用户分数不留痕。

### 9.5 多端互动场景清单（对照验收标准 2）

| 触发方（端 A） | 接收方（端 B） | 消息类型 | 落库与推送 |
|---|---|---|---|
| 学生预约成功（小程序） | 该学生 + 场馆管理员端 | 预约成功 / 新预约提醒 | `notification` 落库 + WS 推送 + 管理端列表刷新 |
| 学生发起拼场 | 被邀请队友（小程序/H5/APK） | 拼场邀请 | 同上；队友端红点提示 |
| 队友接受并满员 | 全体成员 + 发起人 | 成团通知 | 同上；生成预约单 |
| 他人取消预约 | 候补用户 | 递补可确认（10 分钟倒计时） | 同上；倒计时结束自动顺延 |
| 管理端封禁某场地时段 | 已预约学生 | 预约变更/退款模拟通知 | 同上；预约状态置 `CANCELLED` |
| 学生违约未签到 | 学生本人 + 管理端 | 违约扣分通知 | 同上；信用分流水可查 |

## 10. 多端互动与消息规范

1. **通道**：WebSocket（STOMP over SockJS）`/ws/notice`，连接时携带 token 鉴权，服务端按 `userId` 维护会话表 `Map<Long, Set<WebSocketSession>>`。
2. **消息体规范**：

```json
{
  "msgId": "1729000000001",
  "type": "TEAM_INVITE",
  "title": "拼场邀请",
  "content": "同学邀请你加入 10月20日 15:00 羽毛球 2 号场拼场",
  "bizType": "TEAM",
  "bizId": 10086,
  "createTime": "2026-10-16 15:00:00",
  "read": false
}
```

3. **消息类型枚举**：`RESV_CREATED / RESV_CANCELLED / RESV_REMIND / TEAM_INVITE / TEAM_FULL / TEAM_DISSOLVED / QUEUE_PROMOTED / CHECKIN_REMIND / CREDIT_CHANGED / ADMIN_NOTICE`。
4. **可靠投递**：先落库（`notification`）再推送；前端收到 WS 消息后按 `msgId` 去重；重连后调用 `/notifications/poll?lastId=` 补齐增量，保证不丢消息。
5. **一致性要求**：任何"状态变更类"业务，必须在同一事务内完成「业务表变更 + 消息落库」，推送失败不影响主流程（推送异常仅记日志）。

| 风险 | 规范 |
|---|---|

| HTTPS | Let's Encrypt（certbot）或云厂商免费证书，自动续期 |
| 日志 | `journalctl -u campus-venue`，日志目录 `/var/log/campus-venue/` |

**方案 B（服务器可装 Docker 时）**：`docker-compose.yml` 编排 `mysql` + `nginx` + `app` 三个服务，数据卷持久化，本地开发仍然不用 Docker。

### 13.2 Nginx 关键配置示例

```nginx
server {
    listen 443 ssl http2;
    server_name venue.example.com;
    ssl_certificate     /etc/letsencrypt/live/venue.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/venue.example.com/privkey.pem;

    root /var/www/campus-venue/h5;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }          # H5 前端
    location /admin/ { alias /var/www/campus-venue/admin/; try_files $uri $uri/ /admin/index.html; }
    location /api/  { proxy_pass http://127.0.0.1:8080; proxy_set_header X-Real-IP $remote_addr; }
    location /ws/   { proxy_pass http://127.0.0.1:8080; proxy_http_version 1.1;
                      proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; }
    location /doc.html { proxy_pass http://127.0.0.1:8080; }
}
server { listen 80; server_name venue.example.com; return 301 https://$host$request_uri; }
```

### 13.3 配置与发布规范

1. **配置外置**：`application-prod.yml` 只存在服务器，仓库提交 `application-prod.example.yml`；数据库、密钥全部用环境变量注入。
2. **发布流程**：本地 `mvn clean package -DskipTests=false` → 产物 `scp` 到服务器 → 备份旧 jar → `systemctl restart campus-venue` → 健康检查 `curl https://域名/api/v1/actuator/health` → 失败则回滚上一版 jar。
3. **数据库升级**：变更脚本随版本提交，发布前先执行 SQL 再启新包；发布前 `mysqldump` 备份。
4. **跨网络访问验证（对应项目要求 4）**：至少用三种网络各访问一次——校园网、手机 4G/5G、家庭宽带；记录访问时间与截图作为验收材料。
5. **域名与备案提示**：大陆服务器需 ICP 备案（1–2 周，第 1 周即启动）；未备案期间先用香港/境外节点或 `cpolar/frp` 内网穿透做临时演示；小程序要求 HTTPS 且域名已备案。
6. **小程序额外要求**：微信公众平台配置 `request 合法域名` 与 `socket 合法域名` 为 HTTPS 域名；开发阶段可勾选"不校验合法域名"便于联调。
